# DNS
Domain Name System

Backbone of the Internet.

## How does it work?
Translates human readable hostname (like www.google.com) to machine readable IP addresses.
Browser connects to hostname (and website like google.com) and DNS resolver translates
this hostname to machine IP address, and the response from this server is sent back to the Browser.

Each TLD servers a different purpose.
When Browser makes a DNS query, it is asking a DNS resolver.
This DNS resolver could be from ISP (Internet Service Providor),
or from popular DNS providers like Cloudfare 1.1.1.1, or Google's 8.8.8.8.

DNS Resolver
- ISP
- Cloudfare 1.1.1.1
- Google 8.8.8.8

If DNS resolver does not have the answer in it's cache, it finds the right Authoritative Nameservers
and ask it.
The Authoritative Nameservers is the one that holds the answer.
When we update the Domain Name Server, we are actually updating Authoritative Nameservers.


## How does the DNS Resolver finds the Authoritative Nameservers?
There are three main levels of Authoritative Nameservers.
We have
- Root nameserver
- Top Level Domain Nameservers
- Authoritative Nameservers

## Root nameserver

Root nameservers stores the IP addresses of the Top Level Domain Servers.

There are 13 logical root nameservers.
Each of these logical root nameservers has a single IP address assigned to it.
There are many physical servers behind IP addresses.
We usually get routed to the one closest to us.


## TLD Nameservers
TLD Nameservers stores the IP addresses of Authoritative nameservers of 
all the domains under them.

There are many types of TLD names.

There are a lot of top level domain nameservers available.
Top Level Domain (TLD) Nameservers
- com nameservers
- org nameservers
- edu nameservers

Countery Code TLDs.
- .de
- .ch
- .uk (amazon.co.uk)
- .au (apple.com.au)

The Authoritative nameservers provides authoritative answers to DNS queries.

When we register a Domain, we register a authoritative nameservers by default.
We can change them to others.

AWS and Cloudfare runs robust Authoritative nameservers.

This design is highly decentralized and robust.

## Typical DNS Query
- User types www.google.com in the Browser.
- Browser first checks it's cache. It answer is not available in the cache, it makes a OS call to try 
to get the answer.
- OS call would most likely have it's own cache too.
- If OS cache doesn't have the answer, it reaches out to DNS resolver.
- DNS resolver checks it's cache. 
- If DNS doesn't have it in it's cache, it asks the Root Nameserver.
- Root nameservers responds with the tld nameservers.
- .com is most common TLD, most likely the answer is already available in the cache in .com tld 
for the request.
- DNS resolver most likely already caches the IPs of the .com TLD servers.
- DNS resolver then reaches out to .com TLD nameservers.
- .com TLD nameservers returns the Authoritative nameserver for .google.com
- DNS resolver then reaches out to .google.com's authoritatie nameserver, and it returns the IP
address of google.com
- DNS resolver then returns the IP address to the OS.
- the OS returns the IP to the browser.


## How to update DNS of a production Server
DNS propagation is slow because there is TTL (Time to Live) on each DNS record.
Some of the TTLs are pertty long.
Not every DNS resolver is a good citizen. There are some buggy DNS resolvers that
don't honour the TTL.

To reduce the risk, we do these things
- reduce the TTL to 60 secs.
before the update actually happens.

This gives ample time to all DNS servers to receive a shorter TTL.
This would allow the DNS update to take effect with a new shortened TTL.

- Leave the server running on the old IP address for a while.
Only decommission, when traffic dies down to a acceptable level.

Since some DNS resolvers does not honour the TTL, this could take some time and patience.
